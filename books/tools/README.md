# books/tools —— 全部脚本

把四本 2027 王道扫描版 PDF 变成可检索的本地 RAG。所有脚本都可以单独跑，按编号顺序执行。

| 脚本 | 作用 |
|------|------|
| `00_build_all.py` | 一键跑完全流程：OCR → Markdown → 切块 → 建索引 |
| `00_get_model.py` | 下载中文嵌入模型 bge-base-zh-v1.5 |
| `01_ocr.py` | OCR 全部页面（多进程，可断点续跑） |
| `02_extract_toc.py` | 从 PDF 书签提取章节树与页码 |
| `03_build_markdown.py` | 版面还原 + 章节挂载 → Markdown |
| `04_chunk.py` | 按章节切分知识块，带书名/章节/页码元数据 |
| `05_index.py` | 建索引：FTS5（BM25）+ 向量 |
| `06_query.py` | **检索入口**：混合检索并输出带页码的引用 |
| `refresh_index.py` | OCR 没跑完时中途刷新索引（`--fts-only` 只刷关键词侧，几秒） |
| `booklayout.py` | 版面还原库（页眉页脚/水印过滤、同行合并、段落切分） |

### 需要重新调参时才用的辅助脚本

| 脚本 | 用途 |
|------|------|
| `inspect_ocr.py <书名> <页码...>` | 打印某几页的原始 OCR 结果与坐标 |
| `analyze_margins.py` | 统计页边文字出现频率，用来定页眉/页脚/水印的阈值 |
| `peek_front.py <书名> <起> <止>` | 只 OCR 一小段页面，用于调试版面 |
| `test_detect.py` | 在已有 OCR 上验证章节目录识别是否准确 |
| `verify_structure.py` | **结构体检**：每本书 OCR 进度、目录来源、章节文件是否齐全/是否为空 |
| `audit_ocr.py` | **完整性体检**：找出"几乎没识别出文字"的页——这种页不会报错，但等于从 RAG 里消失了 |
| `eval_retrieval.py` | **检索质量评测**：29 道问题分两组，报 hit@1/3/5，并给出失败清单 |
| `audit_loss.py` | **丢失体检**：识别出的文字有多少没进 Markdown（其余体检都只看"有什么"，这个看"少了什么"） |
| `audit_anchors.py` | **锚点体检**：两个书签是否抢同一行（会导致"某节空、邻近节却有两倍正文"） |

## 每天只需要这一个命令

```powershell
python books\tools\06_query.py "你的问题"
```

## 关键实现说明

书籍是**纯图片扫描件，没有任何文字层**，所以必须 OCR。几个影响正确性的要点：

1. **OCR 引擎**：RapidOCR（PP-OCRv4，ONNX）。关掉方向分类器——书页都是正的，
   而它要吃掉约 45% 的时间。
2. **线程必须锁死**：ONNX Runtime 默认 `intra_op_num_threads = -1`（吃满所有核）。
   多进程时会造成严重超订，实测吞吐会掉到 1/50。每个进程锁 1 线程。
3. **版面还原**：渲染尺寸 1353×1885，据此定标——
   - y < 9%：页眉（书名 + 书上页码）。丢弃，但把页码留下来做引用。
   - y > 93%：出版社水印（"配套课程公众号【研大】"/"联系微信…"）。丢弃。
   - 标题"1.1"和"操作系统的基本概念"常被切成两个框，必须按行合并。
4. **组成原理没有书签**，章节结构由正文重建：
   - 章标题的字号很大，但**章号是花体字，OCR 读不出来**，所以章号是**数出来的**，不是读出来的。
   - 小节靠 `N.N` / `N.N.N` 前缀识别，并排除两种干扰：`1.5GHz` 这类计量、
     `3.1节介绍的` 这类交叉引用。
   - 目录页也是编号列表，会被误判成标题；用"章标题必在页面上部"把它排掉。

## 检索侧的一个关键修正

最初把查询词全部 OR 起来交给 BM25，结果"进程和线程的区别"排第一的是讲虚拟化的段落。
原因：语料只有几百个块时，"进程"出现在 63% 的块里，**词频**而不是**主题**决定了排名，
长段落光靠"的/和"就赢了。

现在 `06_query.py` 的做法：去掉虚词 → 统计每个词在索引里的文档频率 →
用最稀有的 2–3 个词做 **AND**（必要时退回 2 个、1 个）→ 仍不够才用全量 OR 兜底。

**还有第二个坑**：即便关键词侧把正确段落排到了第 1，融合时仍可能输。
问「银行家算法」时，排在前面的是"算法效率的度量"——它在**向量侧排第 1、关键词侧排第 17**，
两路相加（RRF）就压过了只在关键词侧排第 1 的"利用银行家算法避免死锁"。

所以现在融合的是**三路**：关键词、向量，再加一路「真正在讲这个问题」的结果。
修完之后同一问题直接返回 `2.4.3 死锁避免 > 2．利用银行家算法避免死锁 (p164)`。

第三路本身有两种形态，按"有多具体"依次尝试：

1. **整句短语查询**。中文合成词常常不是 jieba 的一个词——「循环队列」在索引里是
   `循环` + `队列` 两个词。只有短语查询（`"循环 队列"`，要求相邻且同序）才能把
   "真的在讲循环队列"和"碰巧两个词都出现过"区分开。
2. **最稀有的那个词**。专有名词（银行家算法）靠这一路赢。

顺序不能反。最初只有第 2 种，问「循环队列」时它选中了「循环」——
而「循环」在 155 个块里都有，于是 `循环链表`、`算法效率` 这些把正确答案挤掉了。
加上短语路之后，评测从 20/21 变成 **21/21**。

## 问"哪一年的真题"时会优先给那一年

"2020统考真题 最小生成树"这类问法很常见。真题在正文里长这样：`19．【2019统考真题】对n个互不相同的符号进行哈夫曼编码……`。
问题是"2019""统考真题"这些词本身不太能区分段落，正确答案经常排在第 2 位。

所以问句里出现年份时，含该年真题标记的块会拿到一份额外加权（正好是 rank-1 贡献的一半——
足以把对的那道真题顶上来，又不足以压过明显更贴题的内容）。

**关键细节：年份必须按"真题标记"匹配，不能当成普通的四位数。**
组成原理里满是十六进制地址——`若a的首地址为2020FE00H`——裸数字匹配会让这种段落白拿加权。
所以只认 `2019统考真题` 或 `【2019` 这两种形态。

效果：`2019统考真题 哈夫曼树` 从第 2 位升到**第 1 位**，直接命中那一道真题。

## 查不到东西时会明确说出来

考点还没 OCR 完时，与其返回一个无关章节（考生会照着错的地方复习），不如说清楚。
`06_query.py` 会检查「最稀有的那个查询词」是否真的出现在结果里（正文**或章节标题**里出现都算——
正文常常不重复自己的标题）；一次都没出现就打印告警，提示该章节可能尚未建好。

## 一个只有系统评测才能发现的 bug（rowid 错位）

	extbf{这个 bug 抽查是查不出来的，必须跑整套评测。}

SQLite 普通表的 rowid 从 **1** 开始，但我当初给 FTS 表播种时用的是 **0**：

```
chunks      rowid 范围: 1 .. 1523
chunks_fts  rowid 范围: 0 .. 1522
```

两表靠 rowid 关联。于是 **BM25 排序是对的，但返回的正文和引用永远是"上一个块"的**。
相邻块通常属于同一小节，所以引用看着完全正常，抽查根本看不出来；
只有拿一批问题系统评测才发现：hit@1 从 15/21 直接升到 18/21，5 条误报的"未收录"告警降到 0。

现在两张表写入时都用显式 rowid，并在建完索引后断言两表 rowid 范围一致，不一致直接抛错。

## 评测跑出来是什么样

评测分两组，因为它们考的是系统的两半：

- **lookup（21 题）**：照书上的说法问，比如"什么是系统调用"。关键词侧和短语侧能扛。
- **paraphrase（8 题）**：故意不用书上的措辞，比如"机器为什么能自动执行程序"。
  这一组**只有向量侧**可能答对，不设这组的话语义这半边从来没被真正测过。

```
lookup      n=24  hit@1=24/24  hit@3=24/24  hit@5=24/24
paraphrase  n=8   hit@1=5/8    hit@3=6/8    hit@5=7/8
TOTAL       n=32  hit@1=29/32
top hit came from the vector list: 32/32
coverage warnings: 0
```

**结论要说清楚：照书上的词问，21 题全部第一条就命中；完全换一种说法问，只有一半能排到第一，
但仍有 7/8 进前五。** 所以 —— 查不到就换用书上的原词再问一次，这不是客套话，是实测差异。

### 其中一个"大白话"失败其实是我自己的 bug

问「为什么进程切换比线程切换开销更大」一直查不到，我起初归因于模型上限。**归错了。**

真正的原因是选关键词那一步选了**「更大」**：它词频低（df=33），按"最稀有"的规则被选中，
可它是个比较级虚词，毫无主题意义。于是整个"关键线索"列表被这个词带偏，
而真正讲这事的「2.1.7 线程与进程的比较」（正文里确实有"切换"）一次都没出现。

把"更大/更小/更高/更低/更好/更快…"这类比较级补进停用词后，选中的变成「线程」，
5 条结果全部落回第 2 章并且都含"切换"。**大白话那组 hit@1 从 4/8 升到 5/8，hit@5 到 7/8。**

教训：**"低频"不等于"有信息量"。** 只用词频挑关键词，会被"更大""一样""部分"这类
又少见又没用的词骗到。

### 还有一处更隐蔽的：停用词会被"兜底逻辑"漏回来

`query_terms` 里原本是这么写的：

```python
content = [t for t in toks if t not in STOPWORDS and len(t) >= 2] or toks
```

问「B+树和B树的区别」时：`B` 和 `树` 都是**单字**（被长度规则刷掉），`和``的``区别` 都是停用词
（被停用词规则刷掉）——**过滤结果为空**，于是 `or toks` 兜底把**全部词原样还了回来**，
包括 `区别`。结果"区别"成了那条查询的关键线索。

**过滤为空时的兜底不能一步跳回"什么都用"，要分级放宽。** 改成先只放宽长度规则，
再不行才用全部词；「B+树和B树的区别」现在选中的是"树"而不是"区别"。

### 一次只改一处——我差点把两个改动一起收下

同一轮里我还往停用词表加了一批"不好/不快/遵守/不同/比较…"，
想法是"这些词没意义"。加完评测从 29/32 **掉到 28/32**。

把两个改动**拆开单独测**才看清：分级兜底是纯收益（29/32，B+树那条也修好了），
而**那批停用词才是掉分的原因**——「一个算法好不好怎么判断」原本靠"不好"这个词
阴差阳错命中了正确小节，去掉它就掉了。

已把那批词回退。这提醒我：**原则正确 ≠ 指标变好**。两个改动一起提交，就分不清是哪个在起作用了。

### 剩下那一个失败，才是真的模型上限

不是流水线的问题，是**嵌入模型的能力上限**。拿唯一彻底失败的那题实测：

问「机器为什么能自动执行程序」，正确答案是组成原理 1.2.2「冯·诺依曼机的基本思想」，
那一块**确实已经算过向量**（embedded=Y），但相似度只有 **0.380**；
而同一章里三块无关内容反而拿到 0.438 / 0.434 / 0.431。模型就是分不出来。

所以这不是调权重、调阈值能解决的。要真正改善只能换更强的模型
（如 bge-large-zh-v1.5，参数量 3 倍、建索引和查询都明显更慢），当前判断不值得。
何况本工作区的消费方是**读前五条的会话**，不是只看第一条的人——7/8 进前五意味着通常够用。

这个脚本是发现前面两个 bug 的唯一手段——抽查发现不了它们，
因为错位的相邻块通常属于同一小节，引用看着完全正常。

### 已知局限：告警查不出"由常用词组成的生僻组合"

告警靠的是"最稀有的那个查询词在不在索引里"，对专有名词有效。
但「循环队列」这类由两个常见词拼成的概念，两个词在索引里都有、只是没连在一起，
告警不会触发。（检索本身现在能查到了，见上面第三路的短语查询；这里说的是**告警**不触发。）

之所以不用"整串子串匹配"来兜底：书里说"基带信号"，正文写的是"基带传输……数字信号"，
整串匹配同样找不到，会把**每一个换句话问的正常问题**都报成"未收录"。
宁可漏报，也不要让告警变成噪音——告警一响就该是真的。

## 两个"标题找错位置"的坑（都会让整节正文跑到别处）

**1. 同一页上的同名标题会坍缩。** 每节的"试题精选"和"答案与解析"里都有一个
「二、综合应用题」，**标题一样、书签页码也一样**。原来的锚点匹配总是返回该页第一个同名标题，
于是两个书签锚到同一行——"试题精选"那一节分不到任何正文，全被答案节吃掉。
修法：按出现次序取第 N 个匹配（`find_anchor(..., occurrence)`）。

**2. 书签页码偶尔差一页。** 例如答案节的标题印在第 210 页，而 PDF 书签写的是 211。
于是"在该页找不到这个标题"，锚点悄悄退化成"该页开头"，前后正文就归错了节。
修法：找不到就在相邻页（±1、±2）里再找一次；实测**找回 89 个锚点**（数据结构未匹配数 218→129，
计算机网络 55→44）。

## 已知的版面残留：插图会被"压平"

原书里的**插图**（如"图3.2 从协议的层次上看数据的流动"）在 OCR 后没有结构可言：
图里的标签会连成一串正文，图题也常和后面的正文粘在一段里。
例如：

> 图3.2从协议的层次上看数据的流动然而，在学习数据链路层时，我们通常聚焦于……

- **对检索没影响**：图题本身（"图3.1主机H1向H2发送数据"）反而含有用关键词，正文也是完整的。
- **对阅读有影响**：读者会看到一串图内标签，别把它当正文引用。
- 全书约 300 处图题与后续正文粘连。

**不要试图用"空格多就是图"之类的规则去过滤**——实测过，这条规则会误伤：
选择题的选项（`A．物理层 B．数据链路层`）、代码片段、答案里的算式，
都天然带空格。我按这条规则筛出 984 行"疑似图内文字"，抽样一看绝大多数是**正常内容**，
按它过滤等于删掉一大堆真题和代码。宁可留着这点噪音。

## 一把锁：刷新作业不能和流水线抢文件

索引是**原子替换**的，所以边重建边查询不会读到半个索引。但"原子替换"只保护**单个文件**。

`03_build_markdown.py` 是**先删掉整章再重写**的，而刷新作业和流水线会写同一批文件。
两者撞上时，流水线可能读到"删了一半"的章节，切出的块数变少，索引跟着变少——
而且**之后的核对查不出来**：块文件和索引都同样少，两边数字一致，看起来完全正常。

所以加了一把锁：流水线跑内容三阶段（03→04→05）时持有 `rag_data\.build.lock`，
刷新作业看到锁就跳过这一轮；锁超过 30 分钟视为失效（进程被杀不会永久堵住刷新）。
OCR 那几个小时**不持锁**——那段时间正需要刷新作业把索引跟上去。

## 向量是增量复用的，不是每次重算

id 用内容哈希还带来一个直接好处：**同 id 的向量永远有效，可以直接搬过来用**。
所以 `05_index.py` 建向量前会先读旧索引，只对**新出现的块**做嵌入：

```
[vec] 2421 chunks: 1078 reused, 1343 to embed
```

省掉 45% 的计算，而且这个比例会随书籍越来越完整而继续上升。
如果没有内容寻址，每次重建都得把全部几千块重算一遍。

> 顺带一提：更好的向量覆盖**并没有**改善"大白话提问"的命中率
> （覆盖率从 1079/2874 提到 2421/2877，paraphrase 的 hit@1 仍是 4/8）。
> 这反过来证实了那个判断——瓶颈是模型本身，不是覆盖不够。

## 知识块 id 用内容哈希，不用序号

页面是边 OCR 边入库的，同一章在不同时刻会切出不同数量的块。如果 id 用递增序号，
新内容一插进来，后面所有 id 都会指向别的正文，而**已经算好的向量还挂在旧 id 上**——
检索就会把语义相近的向量配到错误的段落上。所以 id 是 `书名 + 正文 sha1 前 16 位`：
内容不变，id 就不变，向量永远对得上。

## 实测性能（这台机器：R7 5800H / 16 线程 / 16GB）

| 配置 | 吞吐 |
|------|------|
| 单进程 1 线程 | 0.066 页/秒 |
| 4 进程 1 线程 | 0.130 页/秒 |
| 8–10 进程 1 线程 | 0.133 页/秒 |
| 1 进程 全核 | 0.125 页/秒 |

即吞吐在 4 进程后到顶（约 0.13 页/秒），这是**整机资源上限**（桌面端 DSH 自身就占约 2.4 个核），
不是配置问题——再堆进程只会增加发热与上下文切换。全部 1432 页约 2–3 小时。
CPU 未被降频（实测 3201/3201 MHz）。
